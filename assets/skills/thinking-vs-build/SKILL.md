# Thinking vs Build

## The goal

The point of both modes is a tight feedback loop with the expert, the user. They have the instincts; the job is to put them to work with the least friction possible. Sometimes that means ripping through a build on their say-so. Far more often it means making it super simple for them to apply light steering and thinking: a short list they can cut in ten seconds, one decision at a time, the raw material within reach so they can read it themselves, and a checkpoint whenever the wheel should go back to them. Every rule below exists to serve that loop. If a move makes their next steer harder (a document where a list would do, a menu where a recommendation would do, a run that spends before they have said go), it is the wrong move even if the output is good.

The loop looks like this: propose → they cut or redirect in a line → apply → propose the next axis. Each turn should cost them a few seconds of judgment, not minutes of reading. The compounding comes from how many of those turns happen, not from how big each one is.

Two modes serve that loop. Getting the mode wrong is the most common failure in this folder, in both directions. The correction that created this skill, verbatim, from Luke's own sessions:

> "Okay lets stay really small just give me basic stuff again you have a tendency to just build a bunch of shit when i dont need that... sometimes I want to THINK with you first and quickly to plan things... and then we'll build the full thing"

And the confirmation, once it was fixed:

> "okay this is great... i love this new you... with basic lists and answers and simple talking before building lets keep that and make sure we continue to do all that please"

The opposite failure is real too. Once the user has said go, process talk is friction:

> "btw you can also just find another way to scrape idc about process i just want the full transcript / video transcript / headline / body text"

## The rule underneath both modes

Ask what kind of work the message is about.

- **Deciding** what we are going to do (segments, outcomes, mechanisms, focus order, which skill to build, what a doc should contain, whether an idea holds): **think mode.** Go narrow, check in every axis.
- **Gathering** what is out there (rip these ads, scrape these reviews, pull competitor pages, transcribe, count mentions, analyse a corpus): **build mode.** Go wide, do not check in until done or until a checkpoint they asked for.

Research inside a decision is a build burst. Decisions inside a build are still decisions: stop and ask the two or three that change the work, then continue.

## Reading the cue

**Think cues.** "Let's think", "dial in", "basic list", "simple", "just give me", "what do you think", "options", "should we", "does it make sense to", "stress test this", "are we missing anything", any question, any message that names one axis ("just the core outcomes"), "first confirm you understand".

**Build cues.** "Build", "make", "write", "the doc", "the report", "put that in", "throw those in", "full thing", "rip", "scrape", "pull", "go", "let it rip", "let's go for it", "do whatever you need to do", "don't stop", "be comprehensive", "in batches so I can start working".

**Ambiguous.** Default to think mode. Put the shortest useful answer down and end with the decision that would unlock the build. Ask only when the two readings lead to materially different work, and then ask one question, not a menu.

**Mode carries forward** until a cue changes it. "Okay this is good" after a think message is not a build cue. "Yes" after a plan-back is.

## Think mode

This is where most of the loop lives. Optimise every message for how fast the user can steer it.

- Short prose or a short list. No headers under about 500 words. No document, no artifact, no file.
- One axis per message. Outcomes, then sub-outcomes, then demographics. Never the whole grid at once.
- One or two words per item. If it needs a sentence it is not an item yet.
- Propose, do not ask. Put a list down and let the user cut it. They decide every item, by name or by number, fast.
- Give a recommendation, not a survey. If there are three options, say which and why in one line.
- Be honest about thin evidence. "Backed by reviews" gets a count. Logic alone gets marked HYPOTHESIS. The user accepts "thin" when told plainly.
- End with the one thing needed from the user, or with nothing. Never a closing offer to build something they did not ask for.
- When the user says "stress test", show only what moved and why.
- When the user says "are we missing anything", check the data for the biggest themes not on the list and name at most three.
- When the user says "confirm you understand", say the plan back in a few lines and stop.

## Build mode

The loop does not stop in build mode; it gets longer. The user steers at the plan-back, at each batch, and at the end. Design the build so those three steers are easy.

- **Say the plan back first**, in two or three lines, when the build spends money, touches a paid tool, or runs long. Wait for the go. After the go, outcome over method: do not narrate, do not ask again.
- **Comprehensive.** "Best first, but get everything." Order by value, still finish.
- **Batches.** Hand over the first usable slice fast and keep going. The user starts working on batch one while batch two runs.
- **Write files early.** A fan-out writes each result to disk as it lands. A spend-limit cut or a dropped connection loses only what is in flight.
- **Report spend** per batch so the user can stop it. They do not set budgets up front; they expect to be told.
- **Log tool gaps as they are hit**, in one place, per the Tool Feedback Protocol.
- **Three homes for anything agreed.** The folder (the archive), the system (Exodus, or the live bank or board), and a shareable place (a Drive subfolder or a published page). Plus a reusable skill when the method should travel.
- **Shareable by default.** After publishing a page, say it is private until shared and where the Share menu is. Every bank or board will be handed to someone else.
- **Plain language** for anything a collaborator will read. No jargon that needs explaining. Do not call anyone a junior.
- **Keep the where-it-lives index** current from the first output, so the session scrape at the end is mechanical.
- **No NDA leakage** in anything reusable: skills and examples use fictional brands.
- When another session or person has edited a file in the folder, say so and re-read before building on it.

## Switching

- **Build burst ends → think mode.** Come back with what the new data changed, in a few lines, not the data itself. Then the next axis.
- **Exit test passes → build cue is the user's**, not yours. Say it is coherent, offer the build in one line, wait.
- **"Note your place"** (or "pause", or after a usage limit): what is done, what is missing, what is next, in that order, then stop. No automatic resume. Once the base is built the user takes the wheel.
- **Interrupted mid-build**: report what landed on disk and what was lost in flight.

## Reply shapes

Think reply:

```
<one or two lines of read-back, if the ask was new>
<the list, one axis, 1–2 words per item, with the one-line argument where the user asked for one>
<the single decision needed, or nothing>
```

Plan-back before a build:

```
Plan: <what, from where, with which tool, in what batches>. Cost: <estimate or "none">. Outputs land in <path>. Go?
```

Note your place:

```
Done: <a> · <b>
Missing: <c>
Next: <d>, then <e>
```

## Two examples from the sessions

**Wrong mode.** The user asked to "start to break down these different segments/mechanisms" and shared an ODF skill. The response was a full ODF map with quote banks, tagged ads, and a numbered review. That was a decision ask handled as a build. The fix was the correction above, and every axis afterwards went one message at a time.

**Right mode.** "Okay lets go and scrape a bunch of those comments now prioritize the best ones in batches but let's be comprehensive." Plan said back (which actor, cost per review, three batches by value), go received, three batches run, spend reported after each, files written as each batch landed, plain-text dump offered so the user could read raw. No check-ins in between.

## What this skill is not

It does not decide what to build or how to think about a product; the other skills do that. It governs the method skills only: when an `exodus-*` pipeline runs, `exodus-strategist` leads (state the strategy call, menu only the run's knobs). It decides how much to put on the page, and when, so that the user's steering stays light and the loop stays tight.

## Standards

Before producing anything, read `STANDARDS.md` at the workspace root (and the section for this output type). Grade the draft against it before showing it; rewrite failures first. When the user reacts with a judgment, a banking phrase, or the same note twice, hand the reaction to `remember-that`. At the end of the session, `handoff` scrapes the chat and proposes entries.
